guest receives no authority replica or mount.

## Start and operate

Supply real observed metadata, an approved connection, the owned fixture origin
and a fresh ignored status filename. These placeholders are not an environment.
The current case has already used its Send; this documents its entry point,
not authority to start another case or submit again:

```sh
python3 test-bench/vm-reading-bridge.py \
  --connection ACTUAL_APPROVED_CONNECTION.json \
  --environment ACTUAL_GUEST_ENVIRONMENT.json \
  --browser-origin http://127.0.0.1:4180 \
  --record .local/test-bench/FRESH_TRIAL_STATUS.json \
  --authorize-handoff --authorize-submit \
  --trial-profile lab-unified-reading-trial-v3
```

Both flags record existing concrete operator direction; they do not obtain
consent, grant OS permissions or convert a prior no-Send case. The explicit v3
selection declares its one known-public reset before the new case begins; it
cannot widen a prepared v1/v2 case. Full environment and origin inputs are
required for submission. Normal session app approvals
retain their real authorization source. Protected access, unrelated content,
target conflict or unexpected authority blocks the dependent action.

1. Select the guest apps and review their returned CUA documentation. Use
   complete fresh AX/screenshot pairs and review their actual agreement. Native
   regular Chrome qualification is separate from the extension-backed adapter.
2. For v3, claim `setup-raise`, await and `settle` its return, then acquire and
   review a distinct fresh pair before claiming `new-conversation`. Use the
   actual Sidebar New action on an owned empty new surface or the known public
   Lab draft only. After its return, acquire and review another fresh pair.
   Claim `reset-public-draft` only if the current actual settable composer still
   matches the pinned public invitation and contains no history. Settle its one
   return, then acquire and review a distinct fresh pair showing the empty
   merged conversation before recording `preflight`. Never replace a private,
   uncertain or mismatched draft. API returns alone establish none of these
   resulting states; if a gate does not match, stop rather than invent a pass.
3. Prepare the owned browser lane, claim and click `browser-probe` once, then
   `settle` its trusted canceled receipt. Prepare the owned desktop lane,
   claim and click `handoff` once, then settle its uncanceled receipt. Inspect
   and confirm only the covered `Open Claude?` prompt naming the owned origin,
   with persistent permission unchecked. These are distinct browser facts.
4. Inspect Claude after launch and record `arrival`. Compare the current public
   draft with the pinned invitation. Report exact and explicitly selected
   `lab-claude-ax-paragraphs-v1` presentation comparisons separately. A matching
   draft is not evidence of submission or source access.
5. Claim `raise`, await its native return and `settle`. Acquire and review a
   **distinct fresh paired capture after Raise returned**. Claim `send` from

6. Inspect a fresh post-Send pair. Record `sent` only from the actual owned

   deliberately weaker and leaves the submitted invitation unconfirmed. Split

7. Inspect the owned reply and public Lab index tool result as described below.
   Close verified owned browser tabs, observe cleanup effects and `finish`.
   Retain the submitted public test conversation for review. Close the ephemeral
   bridge, stop the owned fixture server and remove its temporary forward.

## Inspect and report the actual result

`sent` takes current `selection.scopeIndex`, `messageIndex` and
`ownedUserMessage: true`. `transition` instead selects the actual
`messageBoundaryIndex`. Neither a native click return nor a completed reply
proves which invitation text was submitted.

`inspect-tool` permits only a current selected disclosure inside the owned
tool-result scope naming `https://agentart.work/agent-index.json`. Supply
`selection.scopeIndex`, `controlIndex` and that exact `sourceUrl`. It cannot
click permission, Send, retry, edit or download controls. After disclosure,
recapture before classifying anything.

`result` accepts explicitly owned, current-capture `reply` and `toolResults`
selections through [the evidence classifier](desktop-ui.mjs). Source evidence
requires the actual expanded tool-result provenance, public URL and visible
body. The supported representations are `raw-json-result`,
`processed-source-result` with selected exact identity fields, and
`access-denial`. Assistant prose and Read/Fetch labels alone leave access
`not-observed`. A selected actual denial is `failed`, not successful reading.

For the observed shell failure, the separate named `requestDenial` selection
within `result` identifies the actual tool disclosure, Request label/text,
Response label/body and exact public index URL. Supply
`selection.requestDenial` with `scopeIndex`, `controlIndex`, `requestLabelIndex`,
`requestIndex`, `responseLabelIndex`, `bodyIndex`, `sourceUrl` and, for the
observed sibling variant, optional `contentIndex`. It is inspected separately
from reply or source-success selections. Its narrow binding can recognize only the
one visible curl request and the observed CONNECT403/HTTP000/zero-byte/exit56
failure. The command is read as source text, never executed or persisted by the
recorder. Actual sibling tool-content boundaries must be validated from the
current capture. The optional `contentIndex` selects only an immediately
adjacent tool-content container sharing the disclosure header's parent inside
the same owned completed assistant boundary (`adjacent-tool-sibling-v1`). It
cannot select unrelated siblings or a broad assistant region as provenance. This
failed-request path does not weaken successful-source URL/identity checks or
make unexposed WebFetch content verified.

Completed orientation requires selected visible collection introduction,
access limits and follow-up invitation facts, plus its finished reply control.
An in-progress response cannot qualify completion. Record absence or extraction
limits honestly instead of supplying a synthetic result or another message.

The report separates browser facts, draft comparison, submitted-message
confirmation, source access and reply. It distinguishes an observed interaction
with source success, inspected denial, unobserved source evidence and incomplete
interaction. A weaker visible transition cannot satisfy submitted-invitation
confirmation. A single inspected failure can be a completed application outcome;
it cannot establish successful source acquisition or the three-case MVP.

Retain bounded facts, timestamps, digests, indices and cleanup dispositions;
raw AX, screenshots, draft/reply text, account details and private history remain
transient. Host authority, guest OS/CUA, controller interpretation, clock
correlation, owned fixture receipts and exclusive input remain trusted. GUI
observations establish no transport-byte identity, independent model origin,
comprehension or private intention.

## New-case observation policies and continuation

The 2026-10-24 continuation adds an opt-in submitted-message policy,
`claude-inline-static-v1`. It requires the complete first owned user-message
body and every static text/link part, once in tree order. A declared UI rendering
maps runs of LF to a single space; all other characters remain significant.
The adapter rejects omitted/reordered parts, altered punctuation/spaces,
conflicting link identities and unrelated message boundaries. Exact equality
is recorded separately. This is a rendered invitation claim, not proof of
model-received bytes, model authorship or successful reading. Historical
contracts and failed reports retain their original comparison.

`--submitted-policy claude-inline-static-v1` selects this only when preparing a
new authorized trial. `--previous-case` may identify a finished public trial
whose complete matching first user message and empty composer are currently
observed. The v2 profile can then Raise, recapture and click New. It cannot
open arbitrary history or clear another draft. An already empty fresh surface
needs no New action. V3 still requires its separately declared reset sequence;
it is not interchangeable with v2.

Source inspection is separate. Once submitted context and a completed reply
are recorded, the controller may open the owned completed activity summary
before its hidden source link is exposed. That expected-source binding is
inspection authority only, never evidence of acquisition. Subsequent tool
headers are matched structurally to their own disclosure controls; permission,
Send, retry and response-action controls are excluded.

The opt-in `curl-request-denial-v2` checks the actual expanded native tool's
Request and Response/Error boundaries, one explicit curl GET of the expected
index, and an observed HTTP403 or CONNECT403 denial. It rejects mixed success
responses, uploads and multiple URLs/commands. Adjacent content must belong
to that header in the completed reply. It saves failure facts and digests,
not commands or transcripts. Response byte count remains unestablished;
a proxy error body's length is not source length. The original denial adapter
and successful-source classifier remain unchanged. Assistant prose or an
unexposed WebFetch body cannot establish successful source acquisition.

A post-reboot Chrome startup prompt can be a native container in the main
window or a separate native window. Cleanup requires its exact heading,
shutdown message, unchecked telemetry and unique scoped Close control; page
imitations and changed telemetry are rejected. No restore or persistent grant
is selected. Fresh 30-second capture limits and consumed-action guards remain.
