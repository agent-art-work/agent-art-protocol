# Roadmap

Working roadmap, 2026-10-24. Order and acceptance conditions are proposals for
development; dates and a public release version are not committed. The generic
protocol remains candidate. SDK versions identify packages, not ratification
of the broader protocol.

**Priority update:** finish the reading alpha for operations first. Runner
development, further live Agent trials and artwork expansion are on hold while
the release is prepared. See the
[release checklist](releases/0.1.5-alpha.1/RELEASE.md) and
[operations brief](releases/0.1.5-alpha.1/OPERATIONS.md).

## 1. Public reading alpha — 0.1.5-alpha.1

Expose a useful, narrow starting point: carry a publisher's public reading
context into the visitor's own Agent with the Ask your Agent component.
Continue one protocol; reading is its lightweight use case.

The operator approved public repository/history disclosure and publication of
`0.1.5-alpha.1` as a GitHub prerelease on 2026-10-24. The
[release record](releases/0.1.5-alpha.1/RELEASE.md) identifies the source,
archive, checks and publication procedure. MIT is included, with applicable
upstream notices preserved. Runtime/type bytes match retained 0.1.4.

The exact alpha passed offline installation, 26 installed runtime tests,
exports/receipt and strict type checks, plus 11 browser scenarios. Six
representative captures were inspected. These are bounded reading results;
real-client trials were not rerun for this archive.

Preserve `v0.1.0`, `v0.1.1`, `v0.1.2`, `v0.1.4` and historical candidate
archives. Do not relabel 0.1.4 with changed licensing or metadata. See
[licensing scope](LICENSING.md).

The first release promises public-document handoff and bounded operational
receipts. It does not promise automatic installation discovery, forced Chat
mode, existing-conversation attachment, successful source access or Agent
execution proof. Public status must retain those limits.

**Acceptance:** approved rights/disclosure scope and license; reviewed source
snapshot and archive; installation/type/API/browser checks against that archive;
truthful release notes and compatibility/limitations table. Public repository disclosure and this GitHub prerelease are now authorized.
Registry publication and site deployment still need operator direction.
A registry is optional for the first alpha. A downloadable archive still
requires release and licensing review.

## 2. Qualify the developer bench — resume after release

The bench is used by a developer's coding Agent to test an integration; it is
not installed by site visitors. Maintain the existing
[MVP scope](test-bench/MVP-SCOPE.md),
[runner plan](test-bench/AGENT-RUNNER.md) and
[execution contract](test-bench/EXECUTION-CONTRACT.md).

Completed: dedicated guest observation, scoped host authority, bounded no-Send
focus/type/cleanup checks, Lab handoff/draft arrival and three single-Send cases.
Lab and a second Inshell fixture passed browser matrices. These results have
different scopes and do not combine into a full native-client pass.

Next: make source-result inspection robust across observed activity layouts,
close the remaining owned-surface cleanup gap, then request a separately
authorized qualification run. The prior three Send permissions are consumed.
Keep actual source failure distinct from failure to observe source activity.

**Acceptance:** meet the standing three-consecutive-pass gate with fixed inputs
and code, independent reports for browser/native checks, no recurring human
Send or result relaying, and owned-surface cleanup. A source-denial outcome
can qualify failure handling; it cannot qualify successful reading. Qualify
actual source acquisition separately. No broader client support follows from
one Claude environment. Do not hold the narrow reading alpha hostage to the
full bench MVP; publish only the support claims its evidence earns.

Broader local reuse comes after that bounded gate: bind a developer's actual
owned preview/component and evidence selectors, using the same guards and
report schema. Current profiles reuse a fixture, not an arbitrary app's UI.
Developers need no VM for local browser checks. Real-client tests require
their own qualified environment, accounts and authority. VM orchestration and
a replacement desktop automation engine are outside the reusable MVP.

## 3. Dogfood the reading release with site owners

Start with agentart.work, then Inshell, Pulse and signatures.gallery reading.
Each owner controls content, source policy, theme, placement and deployment.
Integrate the reviewed release using matching package locks; retain Copy and
manual fallback. Keep historical isolated patches as historical evidence.

**Acceptance per site:** actual shipped dependency/archive identified, public
invitation retained exactly, supported style hooks used, browser/clipboard
checks and separately scoped real-client observations recorded. A site owner
authorizes its rollout. Site publication does not publish the SDK or qualify
another site's integration.

## 4. Add consequential artwork participation — later release

Use THOUGHT first and the hypothetical Agent-initiated, multi-round OPEN FIELD
as a contrasting design test. Preserve Work, Participant, Act and Relation
with evidence across them. Preserve who initiated, which conditions and inputs
were accepted, what the Agent contributed and what changed as a consequence.
No universal human-first, alternating-round or final-synthesis rule.

Settle the execution claim and acceptable trust before promising origin proof.
Develop scoped authorization, contribution return/acknowledgment, retention,
recovery and per-claim verification. Artists own artistic rules, media,
composition and consequence checks. The contract owns mint admission.

**Acceptance:** a working real-client participation path, retained contributions
and bounded consequence checks, failure/recovery tests, portable claim reports,
and a public trust/limits statement. Existing reading integrations continue to
work without adopting artwork infrastructure. The next artwork version and
exact wire contract remain open.

## 5. Harden through independent integrations

Stabilize schemas and compatibility only after different developers and
artworks exercise them. Expand client/version matrices, privacy and retention
guidance, recovery behavior and verification fixtures using observed needs.
Version reports and immutable release inputs. No certification of model
authorship, private intention or blanket genuineness is planned on the basis
of signatures or browser receipts alone.

Managed Agent hosting, a universal model runtime, universal mint gating,
mandatory blockchain, automatic proof of private intention and production
deployment infrastructure are outside the current scope.
